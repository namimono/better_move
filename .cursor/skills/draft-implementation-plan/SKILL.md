# 编写需求实施方案

把需求事实、系统现状和设计决策分开处理，生成可评审、可开发、可测试的实施方案。不要把推测写成已确认事实，也不要细化到具体代码行。

## 选择交付范围

根据用户目标选择输出深度：

- 用户只要求梳理或澄清需求：只完成 PRD Break。
- 用户要求技术方案或完整实施方案：完成 PRD Break，通过需求门禁后再完成技术方案。
- 用户提供多块相对独立的业务：先按业务闭环、系统边界和发布耦合度拆分子方案，再逐份编写。
- 用户指定既有模板：保留其顶级结构，在不破坏结构的前提下补齐必要内容。

完整方案优先复制 [assets/implementation-plan-template.md](assets/implementation-plan-template.md) 后填充。不要在最终文档中保留空章节、模板提示或无意义占位符。

## 建立事实基线

1. 收集正式 PRD、用户补充、确认记录、原型、历史方案、代码库和数据库资料。
2. 明确资料的用途与时效：需求资料说明“要做什么”，代码和数据库说明“当前如何实现”。两者冲突时显式记录差异，不用一方静默覆盖另一方。
3. 建立证据台账，将结论标为：
   - `已确认`：有正式需求、明确确认记录或用户当轮指示支持。
   - `现状事实`：已通过代码、配置、表结构或接口定义核验。
   - `设计决策`：为满足需求作出的技术选择，需要给出理由和影响。
   - `待确认`：资料不足且不同答案会改变范围、流程、数据或验收。
4. 搜索代码时先用 `rg`/`rg --files` 定位工程、路由、接口、DTO/VO、枚举、表、状态机、事务、锁、调用方和测试。引用文件路径、符号或表名作为依据；找不到时写明未核验。
5. 不因原型存在某字段就默认实现。记录 PRD、原型、确认结论和现状之间的差异，并明确最终采用口径。

## 第一阶段：完成 PRD Break

开始前完整阅读 [references/prd-break-guide.md](references/prd-break-guide.md)。

按“背景与目标 → 范围与角色 → 主流程 → 功能规则 → 数据对象 → 异常边界 → 验收 → 确认项”的顺序收敛需求：

1. 结构化转述原始需求，不额外扩展功能。
2. 明确本期包含与不包含，尤其写清历史数据、配置能力、修改能力、数据权限和上下游业务是否纳入。
3. 对每个功能写清触发条件、前置状态、处理规则、成功结果和失败结果。
4. 为每个本期需求或能力编写一个或多个验收用例，按需求分组并统一使用 `| 编号 | 给定 | 当 | 则 | 测试结果 |` 表格；初始测试结果填写 `未执行`。
5. 使用稳定且全文唯一的 `AC-` 编号。更新已有方案时保留原编号和已回填结果；只为新增用例追加编号，不因排序变化整体重编号。
6. 对状态、枚举、默认值、唯一性、必填性、可修改性、权限、幂等和历史数据逐项追问。
7. 将已确认和待确认事项分开。为待确认项标注 `P0/P1/P2`、影响和建议口径。
8. 用结论段说明是否具备进入技术方案阶段的条件。

执行需求门禁：存在会改变系统边界、核心流程、数据模型、接口契约或验收标准的 P0 待确认项时，不输出单一确定方案。优先向用户确认；若用户要求先出草案，则列出条件化方案和明确假设。

## 第二阶段：设计技术方案

开始前完整阅读 [references/technical-solution-guide.md](references/technical-solution-guide.md)。

只从已确认需求和已核验现状推导设计：

1. 定义方案目标、设计原则、系统边界和不改造范围。
2. 画出端到端架构或数据流，说明各端、BFF、核心服务、存储和外部依赖的职责。
3. 设计字段、枚举、表结构、索引、默认值、空值和历史数据策略；避免复用语义不同的既有字段。
4. 按业务能力列接口入参、出参、校验、权限、核心处理和兼容方式，不要求写到类或代码行。
5. 描述主流程、状态变化、事务边界、幂等、防重、异常回滚和多数据对象一致性。
6. 覆盖前端交互、服务端防御性校验、国际化或展示兜底；不适用的层明确写“不涉及”及理由。
7. 给出数据库、核心服务、BFF、前端等兼容发布顺序，以及可回滚性和核心验证点。
8. 复述本期不实现的技术能力，防止实现阶段越界。

## 做需求到设计的闭环检查

交付前建立追踪关系，确保每条本期需求至少映射到：

- 一个设计落点；
- 一个接口、页面、数据对象或流程影响；
- 一个或多个可观察、可判定的 Given-When-Then 验收用例及稳定 AC 编号。

同时检查：

- 文档是否混淆产品“类型”等同名概念；
- 数据是否在申请单、审核、主数据、列表和详情间保持同一口径；
- 客户端传值是否在服务端重新校验；
- 历史空值、旧调用方和混合版本发布是否安全；
- `本期不包含` 是否在技术方案中重新引入；
- 已确认、现状事实、设计决策和待确认是否被误写为同一种语气。

## 验证文档

保存 Markdown 后运行：

```bash
python3 scripts/validate_plan.py /absolute/path/to/implementation-plan.md
```

脚本检查双阶段结构、关键主题和残留占位符。修复错误，并人工处理所有警告；对必须采用完整模板的交付，可增加 `--strict` 让警告导致失败。

## 输出约束

- 使用明确、可验证的陈述，避免“相关处理”“按需支持”“保持一致”等无落点表述。
- 表格适合范围、数据对象、接口、确认项和追踪矩阵；Mermaid 适合跨三个以上组件的数据流或带分支的状态流程。
- 保持业务词汇和技术字段的映射稳定；首次出现时给出定义。
- 优先写模块级改造与核心逻辑，不罗列每个文件或具体代码行。
- 若无待确认项，仍保留“待确认事项：无”，明确需求门禁已通过。
- 验收用例的测试结果只使用 `未执行`、`通过`、`不通过`、`阻塞`、`不适用`；`不通过`或`阻塞`时可在同一单元格追加简短原因或缺陷链接。
