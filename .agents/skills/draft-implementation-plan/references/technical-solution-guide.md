# 技术方案方法

## 目录

- 设计输入
- 系统与工程边界
- 数据与接口设计
- 流程与一致性
- 兼容、发布与验证
- 需求追踪
- 常见缺陷

## 设计输入

只使用三类输入：已确认的需求规则、核验过的系统现状、明确标注的设计决策。不要把尚未确认的产品规则包装成技术结论。

技术方案要回答“哪些系统为什么改、数据如何流转、关键规则在哪里生效、怎样兼容和验证”，不需要回答具体哪一行代码如何修改。

## 系统与工程边界

先列出每个工程或模块的现有职责和本期改造，再列出明确不改造的系统。至少核验：

- 页面路由和前端入口；
- 前端到 BFF、BFF 到核心服务的调用链；
- 核心领域模块、正式主数据和流程数据；
- SDK、消息、定时任务和外部系统消费者；
- 是否存在名称相似但语义不同的旧模块或旧字段。

跨三个以上组件时用 Mermaid 数据流图。图后补充文字说明关键责任，避免只给图不解释。

## 数据与接口设计

### 字段和枚举

为业务文案、API/语言字段、数据库字段和枚举值建立映射。明确 `NULL`、默认值和未知值的含义。若旧字段语义不同，创建独立字段并说明不复用原因。

### 表结构

对每个表说明：字段类型、可空性、默认值、数据来源、写入时机、查询用途、历史策略和索引考虑。索引结论应结合租户隔离、有效标识、查询条件和生产数据量；未取得执行计划时写“需结合执行计划确认”，不要假称已确定。

区分流程数据与正式主数据。若审核后需要二者一致，明确最终值如何确定、何时回写和事务边界。

### 接口

按能力列接口改造清单，而不是堆砌 URL。每项至少说明：

- 调用方和服务方；
- 入参变化、必填性与允许值；
- 出参变化和空值展示；
- 权限、状态和防篡改校验；
- 核心处理和写入对象；
- 旧调用方不传字段时的兼容行为；
- 失败码或用户可理解的失败结果。

所有客户端限制都应在可信服务端重复执行。不要仅依赖 URL 参数、前端只读控件或 BFF 校验保护领域数据。

## 流程与一致性

为正常路径和关键分支写出编号流程或 Mermaid 流程图。重点覆盖：

- 普通入口与特殊入口；
- 状态已有值与缺失值；
- 审核通过、驳回和取消；
- 编辑、重新进入和重复提交；
- 主体创建、关系创建和下游同步是否在同一边界。

明确一致性策略：

- 哪个数据源是最终权威；
- 是否复用现有事务、状态机、锁和幂等键；
- 数据写入顺序及失败回滚；
- 重复请求的返回行为；
- 多系统无法原子提交时如何补偿和告警。

不要只写“保证一致性”，必须指出一致性边界和机制。

## 兼容、发布与验证

### 兼容性

分别处理：

- 历史数据是否补数、代码映射或保持空值；
- 旧调用方不传新字段；
- 新旧前端、BFF、SDK 和核心服务混合版本；
- 列表“全部”与精确筛选是否包含空值；
- 未知枚举、异常字段和展示占位；
- 现有状态机、权限、资质或其他相邻流程回归。

### 发布顺序

按兼容性依赖排列数据库、核心服务/SDK、BFF、前端、配置和数据任务。说明每一步为什么可与前后版本共存。若涉及不可逆 DDL、补数或消息格式，补充回滚和观察方案。

### 验证

验证点必须覆盖需求分支和技术风险：

- 正常、非法、空值、历史和重复场景；
- 页面、接口、申请数据和主数据的一致性；
- 权限边界及客户端参数篡改；
- 失败回滚、重试和并发；
- 列表筛选、详情、导出及下游消费者；
- 相邻旧功能回归；
- 发布期间混合版本调用。

## 需求追踪

复杂方案增加追踪矩阵：

| 需求/规则 | 设计落点 | 数据或接口影响 | 验证点 | 状态 |
|---|---|---|---|---|

状态只使用“已覆盖、待确认、不适用”。发现需求没有设计落点时补设计；发现设计没有需求来源时删除或标为明确的工程治理项。

## 常见缺陷

- 只转述 PRD，没有核验现有实现和系统边界。
- 方案具体到文件或代码行，却没有说明端到端数据流。
- 同名旧字段被错误复用，导致既有语义和下游逻辑被污染。
- 只描述新增字段，没有说明存量空值和旧调用方。
- 前端做只读或枚举限制，服务端直接信任入参。
- 审核状态成功但附加数据写入失败，形成半成功状态。
- 发布顺序没有考虑 SDK、数据库和混合版本兼容。
- 验证点只是需求标题，缺少输入状态和可观察结果。
- 技术方案重新引入 PRD Break 明确排除的能力。
