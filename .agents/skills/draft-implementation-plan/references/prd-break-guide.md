# PRD Break 方法

## 目录

- 资料优先级
- 需求拆解步骤
- 必查规则
- 待确认事项分级
- 验收标准写法
- 阶段完成标准

## 资料优先级

不要将所有资料当成同一种证据。按以下方式处理：

1. 用户当轮明确指示和已确认结论决定最终需求口径。
2. 正式且当前有效的 PRD 定义产品范围；简化版或后续补充可覆盖早期 PRD，但必须记录变化。
3. 原型用于说明页面和交互；若与当前 PRD 冲突，记录差异并按确认后的需求执行。
4. 代码、接口和数据库用于核验系统现状，不自动决定新需求口径。
5. 历史方案只能作为背景，不默认对当前版本仍然有效。

若资料权威性或时效无法判断，将冲突列入待确认事项。

## 需求拆解步骤

### 1. 结构化原始需求

忠实整理需求方描述。把页面、接口、数据、流程和术语分组，但不要补充未提出的能力。原始需求与分析结论分章书写。

### 2. 提炼背景和目标

背景回答当前问题和已有能力；目标回答上线后可观察的业务结果。避免用“改造某接口”替代业务目标。

### 3. 固定范围边界

分别列出本期包含和不包含。重点核对：

- 新增、修改、删除和仅更名；
- 页面展示、筛选、导出和编辑是否分别纳入；
- 新数据、存量数据、补数和迁移；
- 主体属性与主体关系；
- 配置能力与固定枚举；
- 当前流程与关联的后续交易流程；
- 审核、变更审核和审核后维护是否属于同一范围；
- 数据权限、菜单、通知、审计和外部系统同步。

### 4. 定义角色、名词和同名概念

为业务角色、主体、状态、类型、编码和数据对象给出本文定义。若现有系统中存在同名不同义字段，提前区分产品文案和技术字段。

### 5. 还原主业务流程

从触发者开始，依次写出入口、前置条件、用户动作、系统判断、数据保存、人工处理、最终状态和查询展示。分支必须写出选择条件；跨系统时写清数据由谁产生、谁保存、谁消费。

### 6. 逐功能写规则

每个功能至少回答：

- 谁在什么入口触发；
- 需要满足什么身份、状态或权限；
- 页面展示什么、是否可编辑；
- 提交哪些数据，哪些字段必填；
- 服务端如何校验，失败如何提示；
- 成功后写入哪个数据对象并改变什么状态；
- 后续列表、详情、导出和下游如何看到结果；
- 取消、重试、重复请求和部分失败如何处理。

### 7. 建立页面和数据对象矩阵

页面矩阵按“端—页面/场景—本期改造”列示。数据对象矩阵按“对象—调整—来源—去向—历史策略—确认状态”列示。它们用于发现遗漏，不替代详细规则。

## 必查规则

对每个新增或变化的字段检查：

- 业务含义和技术含义；
- 取值范围、枚举和非法值；
- 必填或可空；
- 默认值由谁设置；
- 唯一性范围和空值是否参与冲突；
- 是否允许修改，在哪个阶段修改；
- 大小写、空格、长度和格式；
- 历史数据展示、筛选与迁移；
- 列表、详情、导出和接口是否同口径。

对每个流程检查：

- 登录、身份、角色和数据权限；
- 状态判定顺序；
- 直接 URL、刷新、回调和登录过期；
- 审核通过、驳回、取消、重复提交和失败重试；
- 申请单与正式主数据的写入时机；
- 客户端参数能否被篡改；
- 是否需要事务、幂等、防重或审计；
- 旧页面和旧调用方是否继续工作。

## 待确认事项分级

| 级别 | 判定 | 典型影响 |
|---|---|---|
| P0 | 不确认就无法形成单一可靠方案 | 系统边界、主体关系、状态机、核心数据模型、安全规则、上线范围 |
| P1 | 可先设计但会影响实现或验收细节 | 必填性、唯一性、修改范围、历史兼容、字段来源、失败处理 |
| P2 | 不阻塞主方案，可在开发前定版 | 提示文案、列顺序、格式、非关键交互和展示兜底 |

每项写成可直接回答的问题，并附上影响范围和建议口径。获得确认后移动到“已确认事项”，不要在两处同时保留。

## 验收标准写法

为每个本期需求或能力建立独立小节，并使用统一表格：

```markdown
| 编号 | 给定 | 当 | 则 | 测试结果 |
|---|---|---|---|---|
| AC-01 | 用户未登录 | 访问受保护业务页 | 跳转登录页，且跳转前不展示受保护数据 | 未执行 |
| AC-02 | 用户当前为个人身份且已有企业身份 | 完成身份切换 | 进入原目标页面 | 未执行 |
```

每列含义：

- `编号`：使用全文唯一且稳定的 `AC-` 编号。短文档可用 `AC-01`；长文档可用 `AC-准入-01` 等模块化编号。
- `给定`：写清角色、身份、权限、入口和数据或流程前置状态。
- `当`：只描述一个可执行动作、请求或系统事件。
- `则`：写出页面、接口、数据库、状态和后续查询中可观察、可判定的结果；必要时同时写明不得发生的结果。
- `测试结果`：生成文档时统一填 `未执行`，验收后回填 `通过`、`不通过`、`阻塞`或`不适用`。`不通过`或`阻塞`可追加简短原因或缺陷链接。

一个需求至少对应一个验收用例；存在分支时拆成多行，不在单行中堆叠多个“当”。按需求能力分别建立 `####` 小节，便于产品、开发和测试共同定位。

更新已存在的实施方案时，保持 AC 编号稳定并保留已回填的测试结果。只为新增场景追加编号；删除或移出范围的用例优先标记 `不适用`并注明原因，避免历史验收记录失去追踪关系。

至少覆盖正常路径、权限或非法输入、空值或历史数据、失败回滚、重复操作和范围外能力未出现。避免“功能正常”“数据正确”等不可独立判断的句子。

## 阶段完成标准

满足以下条件才宣告 PRD Break 完成：

- 背景、目标、范围、角色和主流程一致；
- 核心字段和状态规则明确；
- 关键页面、接口和数据对象没有遗漏；
- 每项本期能力都有至少一个五列表格形式的 Given-When-Then 验收用例，且测试结果已初始化；
- P0 待确认项为零，或用户明确允许按已标注假设继续；
- 结论能够直接约束后续技术方案。
